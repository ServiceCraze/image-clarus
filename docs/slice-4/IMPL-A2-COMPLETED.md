# Step A2 - Freeze stage routing and execution contracts [DESIGN]

**Status:** A2 design complete; no Slice 4 execution engine is implemented. This record selects the A2 design and acceptance scenarios. A3/A4 must reconcile state lifecycle and reporting before A5; newly arising product-visible outcomes remain subject to Product Owner disposition before Phase A closes. Existing requirements are ready by orchestration; no separate REQ-acceptance gate is introduced.

**Scope deviations:** None.

## 1. Scope, baseline, and dependency direction

At inspection the package version was `0.3.6`. Existing `pipeline.py` orders `desc`, `json`, `xmp` for one image and uses `stop` or `continue`; `results.py` reports a single-image nonzero result for a failed stage or `128 + signal`. `description.py` and `structure.py` recover and validate their owned output before deciding `output_exists`; invalid existing primary output fails unless regeneration applies. JSON skips a valid existing output before reading its description. `artifacts.py` recovery can mutate artifacts, including restoration and backup cleanup. `state/accumulation.py` runs after selected stages and requires actual JSON completion or `output_exists` skip; it avoids starting after interruption. The provider currently uses synchronous HTTP; CLI interruption relies on a main-thread exception and a shared single-operation flag. The schema worker and XMP backend own child processes; existing subprocess-pipe selector behavior requires Windows review. These are current observations, not claims that the design below is implemented.

Selected design modules are `src/image_clarus/stage_registry.py` for generic immutable stage descriptors, `src/image_clarus/batch_plan.py` for metadata-only planning, `src/image_clarus/batch_execution.py` for coordinator/actors, and `src/image_clarus/provider_worker.py` for the disposable provider-call child. Existing public stage identifiers, invocation behavior and supported `pipeline` imports remain compatible. Names are design selections for B3–B5 and A5 must reconcile them with A1/A3/A4; paths are not claimed to exist. Registry and planner depend on stage-supplied interfaces, not stage-specific XMP budgeting; coordinator invokes descriptors and consumes structured outcomes. Stage implementations own validation, recovery, prerequisites, generation, publication and result construction. Provider child owns only one model transport call; it cannot mutate artifacts or state. State service and category extraction do not import the coordinator.

## 2. Descriptor and stage-owned authoritative seam

A frozen descriptor holds the stable stage identifier, registry order, `uses_llm`, `skip_if_valid_output_exists`, metadata-only predicted-output predicate, and references to the stage-owned decision and execution seam. Description and JSON are true/true; XMP is false/false. The predicate consults configured regeneration and owned-sidecar existence metadata only. No content reads, artifact recovery, state access, provider or ExifTool work occur in planning.

A stage-owned `inspect(image, config, services, *, inference_allowed)` returns either an actual `StageResult`, or a `needs_execution` continuation owned by that stage. It applies the exact existing stage recovery, output validator, regeneration and ordering logic, including valid JSON skip before description prerequisite inspection. `execute` resumes the same authoritative stage path; do not implement a second independent completion policy. Confirmation can produce `output_exists` only after recovery/validation succeeds. Inspection never invokes a provider. Before transformation, the actor rechecks the stage decision and its permission so changed artifacts and newly completed outputs are handled as today. The existing single-image path uses the same stage-owned seam and preserves public `StageResult`/`PipelineResult` behavior.

For a known-excluded image, a selected LLM stage with a predicted existing output and regeneration off is inspected: a valid result yields genuine `output_exists`, preserving JSON accumulation eligibility; an inspection failure yields the real failure and configured continuation. Missing output after inspection is a `budget_excluded` skip, not inference or a fabricated `output_exists`. A selected LLM stage initially predicted to need work and budget-excluded does not attempt transformation; the budget bypass itself is a distinct planned/actual fact. Selected non-LLM stages remain eligible subject to continuation and their ordinary prerequisites. This interpretation of how a newly invalid predicted output interacts with failure policy is a product-visible design outcome for review before A5, not an assertion of Product Owner approval.

The stage-owned seam is an explicit resumable state machine, not a paused arbitrary Python stack. `inspect` returns `Terminal(StageResult)` or `WorkRequired(stage, image, opaque_stage_context)`; for a known exclusion the latter is converted to `skipped/budget_excluded` without a request. The stage's `start_or_resume(context, provider_result)` returns `Terminal(StageResult)`, `Request(request_id, operation, private_payload, continuation)`, or `Publish(validated_bytes, validator, continuation)`. Stage-owned continuation retains immutable image identity, config snapshot, validated prerequisite/input snapshots, and for JSON the original schema, prompt/description and retry-history/feedback snapshot; only the stage interprets it. A response is either sanitized success bytes/text, categorized provider failure, interrupted, or child failure. `request_id` identifies image, stage and attempt and is checked on return; stale/duplicate results cannot resume or publish. Stage validation updates retry history and may issue the next sequential request up to existing configured retry bounds. `Publish` enters the protected gate and returns the real publication result to the same stage continuation; exceptions produce the existing structured failure. The legacy single-image wrapper drives the same state machine through its provider adapter and returns the same public results.

## 3. Initial classification and runtime decision table

The completed metadata plan records A1 image identity, selection context, immutable stage order and regeneration, predicted output existence and initial route, and one immutable admission class: `ADMITTED`, `NO_LLM_WORK`, or `KNOWN_EXCLUDED`. The first N distinct initially LLM-needy images are admitted, once per image. If N is absent all initially LLM-needy images are admitted. Slots never replenish; already excluded work is never promoted. The coordinator records class independently from actual provider requests, stage results and correction identities. A1's Windows case-alias limitation remains an A5 reconciliation item; do not claim case-insensitive alias deduplication that has not been designed or tested.

| Class and observed stage state | Authoritative decision, continuation and accounting |
| --- | --- |
| Any selected LLM stage, no regeneration, primary valid | Inspect using the stage validator; return real `skipped/output_exists` and continue normally. A valid skipped JSON can contribute after selected stages finish. |
| Admitted, another process creates valid primary before execution | Return real skip; retain initial admission and do not fill the slot with another image. |
| Initially no LLM work, primary missing, valid backup | Recover via stage-owned artifact service, validate and return real skip; no provider call. |
| Initially no LLM work, primary and backup absent | If selected stage prerequisites and policies permit, schedule corrective inference even with full admission; record a distinct corrective-work identity only when the provider boundary is entered. It may exceed N or 2N. No omitted stage is added. |
| No-regeneration invalid existing primary, regardless of initial class when inspection occurs | Report the existing `invalid_artifact` failure; do not overwrite the existing primary with a valid backup or invent correction. Apply `continue`, `stop`, or `abort`. |
| Missing primary and invalid backup | Preserve failed recovery and backup; report actual failure and apply continuation. No fabricated success or inference. |
| Regeneration on | Metadata classifies the selected LLM stage as initial work. An admitted image follows existing regeneration/recovery behavior; known exclusions cannot infer. |
| Known excluded, LLM work required | No selected LLM request, including if files later change; mark budget exclusion rather than successful output. Selected non-LLM stages remain eligible under the configured continuation and prerequisite rules. |
| Known excluded, predicted existing selected JSON is actually valid | Perform stage-owned confirmation without inference; record real JSON `output_exists` and separately the initial budget class. After selected stages, the normal eligible accumulation path runs once if enabled. |
| Known excluded, predicted existing selected JSON disappears | No inference; record budget exclusion, continue to selected non-LLM stage, which applies its own missing-prerequisite behavior. Do not fabricate JSON output or accumulation eligibility. |
| Valid JSON with missing description | The JSON stage returns `output_exists` before its prerequisite check; do not change the existing envelope-validity contract. Earlier selected stages still follow their own outcome and continuation. |
| Omitted stage or missing prerequisite | Never implicitly add a stage. Apply A1's resolved explicit-file/batch policy for the selected stage. A missing prerequisite is not completion. |
| Earlier stage fails but later persisted input is usable | `continue` may run later selected work; `stop` terminates only this image; `abort` stops new batch dispatch. Already active work is accounted for, not assumed never to have started. |
| Signal/worker exception | Apply the shutdown state machine below; preserve actual completed/failed/skipped work and identify active interruption versus queued/not-attempted work. |

**Ordered excluded-image example:** With selected `desc,json,xmp`, a missing description that was known during planning receives `skipped/budget_excluded`; it is a non-failure and therefore does not itself invoke stop/abort. The JSON stage is then considered in registry order:

| JSON condition at execution, regeneration off | JSON outcome | Later XMP and accumulation under each policy |
| --- | --- | --- |
| Predicted existing; valid primary or valid recovered backup | Real `skipped/output_exists`, no request | XMP remains eligible under `continue`, `stop`, and `abort`; real JSON skip makes post-stage accumulation eligible when enabled. |
| Predicted existing; invalid primary or failed invalid-backup recovery | Real `failed/invalid_artifact`, no request | `continue` allows XMP to apply its own validation/prerequisites; `stop` marks XMP not attempted for this image; `abort` prevents new dispatch batch-wide. No accumulation from failed JSON. |
| Predicted existing but primary and backup now missing | `skipped/budget_excluded`, no request | XMP is eligible under all three policies and applies ordinary missing-prerequisite behavior; no JSON accumulation. |
| Initially predicted missing JSON | `skipped/budget_excluded`, no request, including if later changed | XMP is eligible under all three policies and inspects its own persisted prerequisite; no JSON accumulation from the budget skip. |

If the JSON stage is unselected, do not inspect it or infer accumulation; the selected XMP stage applies its own prerequisite behavior. If XMP's own prerequisite is invalid or missing, its real result and configured policy apply. The invalid-confirmation behavior remains an explicitly pending product-visible disposition, not an approved change.

Any external replacement after inspection remains subject to the inherited lock-free sidecar race. Recheck at execution boundaries, but do not claim a lock, snapshot isolation or protection from a concurrent process replacing a validated artifact afterward.

## 4. Concrete coordinator and actor protocol

One coordinator owns the immutable completed plan, per-image lifecycle/result state, queue bookkeeping, stop/abort state, and reporting events. There is **one long-lived stage actor thread per selected stage**, and no other stage actor or confirmation worker. Each actor runs all of its own stage inspection, transformation coordination and publication serially. For an LLM transformation it starts at most one disposable provider-call child, then keeps the request in `INFERENCE_PENDING` while the actor services only lightweight authoritative inspection jobs for other images; it starts no second inference for that stage and does not concurrently execute a second transformation/publication. The child performs only HTTP transport and returns a response or sanitized error, not stage work. Thus one actor and at most one outstanding provider request per stage remain active; inspect work can advance unrelated candidates while a request is pending. Reconcile this explicit meaning of 'one active worker' with the Phase A gate; do not count a provider child as another stage worker or permit hidden stage transformations there. The image whose request is pending retains its per-image token and its stage cannot be declared complete until the response has been validated/published or failed.

For each image the initial predicted downstream queue entry carries a list of earlier selected stages that require actual confirmation; a predicted route is not a stage result. Before executing that image's downstream work, the coordinator orders confirmation requests through owning actors in registry order. An image has a single lifecycle token; a stage has at most one `pending`, `running`, or `terminal` record per image. Pending confirmation or transformation suspends that image's downstream readiness but does not block other ready images. A real skip advances; correction returns the same image to the owning actor and resumes only after its real result; failure follows its configured continuation. Stages omitted by selection have no token or confirmation.

Early-forwarding guarantee: while an upstream actor has an inference response outstanding, it can confirm unrelated candidates and forward them before that inference completes. The actor cannot confirm while itself performing request preparation, a stage validator, filesystem recovery or protected publication. Such local operations can block on the OS; no absolute forwarding deadline or bypass around an active protected operation is promised. The provider-hold barrier verifies the specified inference overlap, and separate pre-request/confirmation/publication barriers verify queued candidates are not falsely marked confirmed and progress after the actor becomes available. The actor/child interpretation of the one-worker requirement remains subject to A5 reconciliation; no additional actor is introduced to hide concurrent stage execution.

The coordinator maintains `PLANNED → CONFIRMING → READY → RUNNING/INFERENCE_PENDING → RESULT → FINALIZING → TERMINAL`; each transition is serialized through coordinator messages. It rejects duplicate enqueue/completion by image ID and stage ID. An actor must never wait synchronously for the coordinator while holding a lock that the coordinator needs. It may do bounded inspection between polling child-result/stop events; filesystem calls are not assumed interruptible. An outstanding request prevents starting a second inference. On each actor turn check stop first, then process a ready provider result before taking at most one FIFO confirmation; after each confirmation recheck the result and stop before taking another. If no inference is pending and transformations also wait, service at most eight confirmations before the next FIFO transformation, then reset the confirmation count. This bounded arbitration prevents a stream of confirmations starving a ready response or queued transformation, and prevents a held inference blocking confirmations, while making no hard time guarantee for a blocking individual operation. Completion order is not deterministic.

Seed all predicted routes only after planning completes. The coordinator closes dispatch only after initial seeding is complete **and** all image tokens are terminal, no queued/running/confirmation jobs or provider operations remain, and all finalization messages have been accounted for. Wakeups use condition/event notifications, not polling an empty queue as proof of completion. Worker exceptions become sanitized explicit failures, wake the coordinator and initiate abort/cleanup rather than silently losing work. The stage actor owns its provider child and any schema/ExifTool children; the coordinator tracks registration and completion so termination cannot strand queues.

On stop/abort or actor death the coordinator, as sole terminal-state owner, removes each queued confirmation/transformation and emits a not-attempted fact for its selected stage; it marks an unprotected active operation interrupted, preserving any earlier terminal stage results. For a dead actor or a child exiting without a valid result, emit one sanitized stage failure unless interruption already owns that operation, cancel all its dependent jobs, initiate batch abort and terminalize affected images. A late completion for an already terminal `(image, stage, generation)` is discarded and cannot publish. A protected operation remains active until its real result and cleanup arrive; the coordinator then drains it and marks remaining stages not attempted. For finalization exceptions record a sanitized state diagnostic, close owned services, preserve primary results, and terminalize once; an explicit cancellation follows the existing state-transaction outcome. An empty plan seeds zero images and terminates once all actors acknowledge startup/shutdown; no synthetic success stage is created. All token transitions and terminal messages are idempotent and coordinator-owned.

Sequential mode uses the same stage-owned decisions, immutable plan classes, permission checks and finalization contract, but processes one image's selected stages and eligible accumulation to terminal before starting another. It uses no additional stage actor concurrency. This ensures the next image can observe the previous image's eligible categories. A3 settles per-image state-service lifetime/fallback ownership while preserving the finalization boundary.

## 5. Failure policies and exit contract

Extend `pipeline.on_stage_failure` from existing `stop`/`continue` with `abort`; default remains `stop`. Add dedicated `--on-stage-failure {stop,continue,abort}` with dedicated CLI > ordered `--set` > selected YAML > defaults. Existing options/selection remain compatible; A1's config validation and singleton conflict rules apply. `continue` advances this image to the next selected stage; `stop` marks later selected stages not attempted for this image and allows unrelated images; `abort` sets batch abort, prohibits new dispatch and requests cancellation of active cancellable work. Already-dispatched work can finish a protected operation or be interrupted, and may have begun before the failure. Explicit-single-image ordinary results retain their existing mapping.

Batch result status is `0` when all attempted operations succeed or are ordinary skips/budget exclusions; `1` if any actual stage fails, a worker fails, or configured abort occurs; CLI/configuration/selection/preflight errors retain their existing categorized exit mapping; handled SIGINT/SIGTERM takes precedence as `128 + signal`. Optional state diagnostics remain visible and do not by themselves change otherwise valid processing success. A4 owns exact output and reconciles these result categories, not a conflicting result policy. A failure is never a successful `output_exists` skip.

Acceptance scenario: hold image B at a dispatch barrier, cause A's early selected stage to fail while A's later stage has valid persisted input. Under `continue`, A's later stage and B can run; under default `stop`, A's later stage does not run and B can run; under `abort`, neither is newly dispatched after abort, though another operation already dispatched before the failure is honestly reported. Assert actual image/stage outcomes and final exit, not an imaginary global ordering.

## 6. Cancellation and protected publication

First handled SIGINT/SIGTERM records the first signal and wakes the coordinator; the handler does not throw asynchronous exceptions into worker or filesystem code. Repeated handled signals do not interrupt an admitted publication. The coordinator atomically closes dispatch and requests cancellation. On Windows only signals/console events actually delivered to the process can be handled; forced termination, power loss and machine failure are not graceful-stop guarantees.

Run the existing synchronous provider operation in a disposable child, one request per child, launched by `subprocess.Popen` with an argument vector and no shell. Send framed request/configuration over private stdin and return a length-delimited sanitized response over stdout, never argv or logs; never persist credentials in temp files or expose them in child diagnostics. A dedicated transport-only writer and reader per child transfer bounded chunks into bounded in-memory queues; they never invoke stage logic or publish artifacts. Actor/coordinator monitor stop, child-exit and transport events without blocking on a full pipe; on stop terminate/reap the child, close the pipe endpoints and join transport helpers. Partial, malformed or absent frames produce sanitized worker failure unless cancellation already won. Bound transfer-buffer usage rather than impose a new product request-size limit; ordinary resource exhaustion is a visible error, never silent truncation. Register and recheck stop as below; cancellation reports interruption rather than waiting for normal provider timeout. Terminating the local child closes its transport but cannot guarantee the remote service stops computation or billing. A provider retry uses the existing retry contract and remains part of the same admitted image, not a new admission slot.

A publication gate serializes the stop/abort transition with permission to begin each mutating recovery or `ArtifactService.write`. The lock is held only for the atomic check-and-increment of a protected-operation count, then released before filesystem or subprocess work. Stop acquires that same lock, changes state to stopping and releases it immediately; every subsequent admission fails while already-admitted operations continue. A `finally` path decrements the count exactly once even on errors. Internal nested recovery invoked by an already-admitted write shares its existing protection token and does not seek a new gate admission; independent recovery must acquire its own token. The coordinator continues cancelling unprotected work while the count drains and cannot finish shutdown until each admitted operation has reported and decremented. No lock is held throughout a blocked write. A recovery/write already entered finishes its existing staged write, validation, backup/replace, verification and cleanup where possible and reports its actual result; never terminate a stage thread during this protected region. If a validator subprocess belongs to an already admitted protected operation, it remains owned by that operation until it finishes or its existing timeout/failure handling completes; cancellation must not kill it mid-publication. Operations outside this region, including provider calls and unprotected schema/ExifTool subprocesses, are registered, cancellation-aware, terminated and reaped with owned temporary-file cleanup. Replace POSIX-only selector assumptions for subprocess pipes with a cross-platform bounded reader strategy in the owning implementation step; do not invoke a shell.

Protected child processes must also be insulated from terminal-generated group signals, not merely spared by coordinator cancellation. On POSIX launch each owned subprocess in a separate session/process group using supported `Popen` process-group facilities before it can enter protected validation; register it and recheck stop after spawn. The coordinator explicitly signals only unprotected owned children and retains ownership through reap. On Windows use `CREATE_NEW_PROCESS_GROUP` for owned children and the available console-control handling appropriate to that process; do not assume POSIX signals or that `terminate()` is graceful. Prevent inherited Ctrl-C from being treated as a request to kill a validator in a protected transaction; explicit forced process termination, console closure and OS failure remain outside the guarantee. Spawn, registration, stop and child-exit races have explicit recheck/reap outcomes; a child already admitted within a protected operation is not terminated by the coordinator on handled stop. Tests on POSIX must send a real process-group signal during a protected validator, not just signal the parent; Windows behavior remains unverified until run there.

Close child-registration races by checking stop before spawn, registering the child before making it visible as active, and immediately rechecking stop. If stop won, terminate/reap an unprotected child; a child spawned within an already-admitted protected operation retains that operation's protection token and is drained instead. Never leave a child unowned after spawn failure, stop or actor exception. Process creation, blocked filesystem syscalls and OS-level process termination/reaping can exceed response targets; report these limitations and do not claim a hard stop-time bound. Safe-write recovery and lock-free cross-process sidecar limitations are unchanged. On interruption do not start optional state accumulation; an already-started state transaction follows its existing commit/rollback and interruption semantics. Preserve real results of operations that completed; mark queued stages not attempted, active cancelled work interrupted, and finalize each image once. Join/reap owned work before CLI exit, subject to documented OS failure limitations.

## 7. Deterministic verification scenarios

These are future test obligations, not executed results:

1. Hold A's description provider response at a controllable local stub; B's predicted existing description and JSON are independently confirmed by their owning actors and B reaches its XMP evaluation before A releases. Measure one actor and at most one outstanding provider call per stage; no hidden confirmation worker performs stage logic.
2. After planning, remove or corrupt B's predicted output. Confirm actual recovery, permitted correction or invalid-artifact failure occurs before B's downstream selected stage executes; another image can still progress. Exercise `continue`/`stop`/`abort`, valid backup, invalid backup and newly created primary without slot replenishment.
3. For N=1, admit one image; three initially no-work images lose descriptions after planning with no backup. If existing stage policies permit correction, four distinct images reach the provider boundary while original admission stays one. A known-excluded image never makes a provider call.
4. Known-excluded image with selected JSON already valid yields real `output_exists`, zero LLM calls, and once-only post-selected-stage accumulation; disabled accumulation adds nothing. Missing/invalid JSON follows the decision table and never fabricates a skip.
5. Use the two-image policy barrier in §5; include actual already-active work in abort accounting. Exercise stage subsets and valid JSON without a description.
6. Send real handled signals during a held provider request, before/after child registration, during an admitted safe publication, while schema/ExifTool work is active, and during state finalization. Check bounded parent responsiveness where OS operations permit, child reap, no new dispatch after stop, publication integrity, truthful partial results and fresh-run resume. Verify repeated signals do not interrupt admitted writes.
7. For Windows-by-design, exercise platform-independent queue/child/pipe contracts on Linux and pure Windows path parsing separately. Do not claim these establish Windows console signaling, pipe behavior, junction handling, or filesystem/runtime success; no Windows test machine is a prerequisite.
8. Hold an actor in pre-request preparation and then an admitted recovery/publication: confirmations remain unconfirmed until it can inspect, then advance without false success. Hold a confirmation while a provider response becomes ready: after that one confirmation, the response is processed before another confirmation. Exercise JSON invalid-response retry snapshots and child failure/cancellation without stale-response publication.
9. Race stop against publication admission, including two concurrent stage publications and nested failed-write recovery; verify count increment/decrement, stop linearization and no new admission. Send a real process-group signal during protected child validation, and test actor exception, child exit without a result, finalization exception and empty-plan terminalization with no stranded tokens.

## 8. Cross-step decisions, rationale and evidence

The staged actor protocol is selected to satisfy early forwarding and one stage worker while avoiding synchronous-provider starvation; the provider subprocess supplies cancellability without killing the publishing actor. It requires B3/B4 stage-seam refactoring, B5 child/actor coordination and C2 real-process barriers. A3 reconciles state-service ownership and finalization, and A4 reconciles event/count/exit presentation; A5 ensures no significant contradiction remains. Exact correction behavior for budget-excluded invalid predicted outputs, the batch exit aggregation, and one-actor-with-pending-provider interpretation are recorded as design outcomes needing Product Owner disposition before Phase A closes if they change product behavior. Existing admitted-image, non-LLM, regeneration and stop/continue/abort decisions are not reopened.

No feature code, live provider, live image or Windows runtime testing was performed. At version `0.3.7`, from the project root: `uv lock --locked` passed (21 packages); `uv run --locked --extra dev --python 3.13 image-clarus --version` reported `image-clarus 0.3.7`; `uv run --locked --extra dev --python 3.13 pytest -q tests/unit/test_cli.py tests/unit/test_resources.py tests/unit/test_pipeline.py tests/unit/test_description_stage.py tests/unit/test_structure_stage.py tests/unit/test_artifacts.py` passed 212 tests; `uv run --locked --extra dev --python 3.13 ruff check .` passed and `uv run --locked --extra dev --python 3.13 ruff format --check .` passed (163 files). The editable-package installation fell back successfully from hardlink to copy. These verify the current baseline and version delivery, **not** the unimplemented actor/child protocol; no full suite was run.

Created `docs/slice-4/IMPL-A2-COMPLETED.md`; updated `docs/slice-4/IMPL-PLAN-slice-4.md`, `pyproject.toml`, `uv.lock` and the two exact-version assertions in `tests/unit/test_cli.py` and `tests/unit/test_resources.py`. No production implementation was changed. Independent read-only review findings on forwarding limits, child signals, atomic write admission, continuations, exclusions and shutdown were incorporated; this does not constitute Product Owner approval or runtime verification.
