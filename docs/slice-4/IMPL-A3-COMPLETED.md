# Step A3 - Freeze state and category management contracts [DESIGN]

**Status:** Design in progress; a native read-only VFS protocol is selected but target-identity and product-visible choices still need disposition. No Slice 4 management command, batch state engine, or acceptance test is implemented here. Requirements readiness follows assignment; no separate REQ acceptance gate is introduced.

**Scope deviations:** None authorized. The proposed restriction on management-command migration and the proposed CWD-only rebuild target are product-visible design choices pending disposition before Phase A closes; they are not represented as previously approved requirements.

## 1. Scope and dependency boundaries

Current state selection, optional fallback, storage and extraction are implemented in `src/image_clarus/state/resolution.py`, `service.py`, `storage.py` and `accumulation.py`; the existing CLI calls optional accumulation after `run_pipeline`. The existing `StateService` mutates its own backend on failure, `MemoryStorage` is not synchronized, and the writable SQLite constructor can migrate. None is a suitable shared mutable management facade or a provably read-only list backend. `_extract` accepts an injected envelope reader; the reader currently lives in `stages/structure.py`. Preserve that direction through composition: management and batch wiring inject the existing authoritative envelope reader into a result-bearing extractor in `state/accumulation.py`; the state domain does not import stages or duplicate the envelope validator. A5 checks that ownership and public compatibility remain correct.

Selected prospective additions are `src/image_clarus/state/management.py` for strict command orchestration and result types, `src/image_clarus/state/readonly.py` for read-only SQLite access, and `src/image_clarus/state/extraction.py` only if the existing extraction function is moved there as the single source with compatible imports; no duplicate implementation is allowed. Extend `state/storage.py` with strict category-only delete and transactional insert counts; A1's `discovery.py` provides enumeration. CLI composes these pieces without importing a provider or XMP backend for management. Proposed tests include `tests/unit/test_state_management.py`, `tests/unit/test_state_readonly.py`, `tests/integration/test_state_management_cli.py`, and `tests/integration/test_state_management_concurrency.py`, plus existing state and pipeline tests. These paths are design selections, not claims that files exist.

## 2. Ordinary process: per-image selection and ownership

Configuration priority is dedicated `--state-dir` > ordered `--set` > selected YAML > defaults. A dedicated/`--set` relative path is relative to CWD; YAML-relative values resolve relative to the YAML file, preserving existing origin handling. An effective null clears a lower selection and resumes discovery. Resolve once per image's context, not once per batch; hold that image's context for all prompt snapshots and its finalization.

| Condition | Selection and ordinary-processing outcome |
| --- | --- |
| Explicit/effective non-null directory | Select exactly that directory for every image; no ancestor search. A valid repository can be shared through independent handles. |
| Explicit selected directory missing, invalid, inaccessible, corrupt or unsupported | Emit sanitized state diagnostic and use that image's temporary memory; never select another persistent repository. |
| No explicit directory; nearest initialized CWD ancestor | Select it for each image even when an image is under a different initialized collection. A selected but invalid candidate is an error, not permission to search elsewhere. |
| No CWD candidate; nearest initialized image-directory ancestor | Select independently for each image. Different collection roots can select different repositories. |
| Accessible ancestor `.image-clarus` directory without database | It is uninitialized; continue searching. An inaccessible/broken entry is an error, not absence. |
| Neither ancestry has an initialized repository | Use shared invocation-local no-store memory, with no diagnostic and no persistent creation. |
| Discovery, open, read, update, migration or close error | Report a sanitized, image-correlatable state diagnostic independent of logging level; preserve otherwise-valid stage results, do not redirect to another persistent store, and use only the affected image's isolated temporary fallback as applicable. |

The coordinator owns a separate service wrapper and lifecycle token for each image; persistent backends use independent handles to the same resolved identity and short transactions. A shared synchronized memory backing serves all images that genuinely selected no repository, allowing image-first runs to see previous no-store additions; each wrapper releases its reference after finalization and the coordinator closes that backing after all images drain. A failing selected-store wrapper switches only itself to fresh per-image memory; it never swaps another image's backend or closes its live handle. A failed read yields an empty snapshot. A failed union rolls back, diagnoses and is not replayed into memory; only later successful additions to that fallback can be observed by that image. Existing SQLite bounded contention and sanitized diagnostics apply; no transaction, cursor or lock spans a provider request, a stage operation, or the full batch. This invocation-wide no-store memory behavior is a batch design decision, not an assertion about prior multi-image behavior.

## 3. Actual-result finalization

The coordinator owns exactly-once post-selected-stage finalization, including when a later selected stage fails, a stage is budget-bypassed, or a handled stop arrives. Finalization is not synonymous with performing optional accumulation. Each eligible image's service is closed after its own finalization; duplicate terminal messages cannot repeat a union.

| Actual image outcome | Optional category accumulation |
| --- | --- |
| Selected JSON `completed`, or selected JSON `skipped/output_exists` | If enabled and no stop is observed, read the actual `.desc.json` bytes once after selected stages terminate; validate/extract and union once. The later stage can have failed; retain its failure. |
| Known budget-excluded image with valid selected JSON authoritatively confirmed `output_exists` | Same eligible path, without inference. Record budget classification separately from real JSON result. |
| Budget-excluded skip, omitted JSON, JSON failure/missing prerequisite or no actual JSON result | No accumulation, even if a file exists. A prediction or budget bypass is never `output_exists`. |
| Disabled, dry run, or handled stop observed before optional work | Do not read JSON for accumulation or open/update state for it. Dry run also does not open, initialize, migrate or write state at any stage. |
| Eligible JSON missing, unreadable, invalid, or replaced after stage | Sanitized optional error; do not regenerate, invent a result or change the primary stage result. Use the actual bytes read; lock-free external sidecar replacement remains possible. |
| State update interrupted before commit | Roll back and close; never replay. If stop races an already executing commit, report the real committed/rolled-back outcome and signal result; no sidecar-state atomicity is implied. |

Sequential mode completes this finalization and closes the image wrapper before beginning the next image. Concurrent images may snapshot at different times; no global taxonomy barrier is added. Check stop before starting an optional operation, before a transaction and immediately before commit; state errors remain visible and nonblocking while `StateStopped` is interruption, not a fallback diagnostic.

## 4. Management grammar and target

The following are chosen CLI designs, not implemented commands:

```text
image-clarus state categories list [--config FILE] [--set PATH=VALUE] [--state-dir DIR]
image-clarus state categories clear [--config FILE] [--set PATH=VALUE] [--state-dir DIR]
image-clarus state categories rebuild SOURCE... [--config FILE] [--set PATH=VALUE] [--state-dir DIR] [--max-depth N | --max-depth-unlimited]
```

Options belong to the operation and obey A1 singleton/conflict and source-origin rules. Resolve only configuration relevant to state and, for rebuild, selection; do not require credentials, provider, stage, prompt/schema or XMP preflight. The destination is one repository for the entire command: effective dedicated CLI directory, then generic override/YAML directory, else nearest initialized CWD ancestor. A null resets lower selection to CWD discovery. Without a selected initialized repository, fail visibly; no temporary-memory success, automatic initialization, image-ancestor discovery, or alternate persistent fallback. Rebuild source roots are inputs only and do not choose a destination; for a source outside the CWD collection the user supplies `--state-dir` as needed. An explicit invalid selection fails, and an accessible uninitialized ancestor is skipped during discovery as in ordinary processing. This CWD-only management context is a selected design outcome for A5's product-behavior review, not an invented prior Product Owner decision.

Example: with an initialized CWD repository A and source collection B, rebuilding B without a directory option targets A, not B; to target B, pass B's repository directory explicitly. Multiple source roots likewise use only that single selected destination. Before any mutation report the target-selection origin (explicit/configured or CWD-discovered) in the operation summary; do not print credentials, category data, raw SQLite errors, or path text in diagnostics. Record normalized selected directory/database identity and use filesystem identity (such as stable file ID or device/inode when available) to detect replacement at preflight and immediately before each transaction; a detected change fails without selecting the replacement. These checks alone cannot close a cross-process replacement race after the last check: do not claim strict pinned-target safety without a platform-supported handle-bound SQLite open and commit protocol. If identity cannot be reliably obtained, or replacement/commit is ambiguous, stop and report the uncertainty; never claim the intended repository definitely received the update. Define this identity binding at A5 and test replacement before open, during a write, and immediately before commit on supported filesystems.

Rebuild accepts explicit `.desc.json` files, directories and A1 native patterns; discovery includes orphan sidecars whether or not the corresponding image exists. Existing explicit-file symlinks follow A1's literal-file rule; discovered symlinks are not followed. Deduplicate overlapping inputs by A1 resolved identity; process in A1 deterministic traversal order with the independent `category_rebuild.max_depth` and depth flags. Each explicit file is eligible by suffix; no sidecar is selected by inspecting its image, XMP, or decoder. Discovery/invalid-source errors prevent mutation and return a command/config error; after completed discovery, individual read/extract errors are per-input failures and do not stop other readable inputs. Inclusion of explicit and orphan sidecars is a selected design outcome for A5 review, not prior Product Owner approval.

## 5. Strict read-only listing and empty-safe access

A list selects an existing target, opens it without initialization/migration, validates application ID, format/domain version and schema, and returns a consistent binary-sorted snapshot. It does not write, create or remove the directory, DB, journal, WAL or shared-memory file, even on error. Corruption, access failure, unsupported/newer version or recognized older version needing migration is a sanitized error, not an empty list. No management command selects memory. Ordinary `SQLiteStorage`, `_connect(mode=rw)` and `immutable=1` on a concurrently writable live DB do not meet this contract.

**Selected design: native fail-closed SQLite VFS**, proposed source `src/image_clarus/state/readonly_vfs.c` and Python adapter `src/image_clarus/state/readonly.py`. Run the reader in a short-lived isolated process so other connections in the CLI process cannot accidentally drop its process-level SQLite file locks. It opens the source with `SQLITE_OPEN_READONLY` and private cache through the wrapper. The wrapper forwards reads, truthful access/existence checks, and native `xLock`, `xUnlock`, and `xCheckReservedLock` to the platform's default VFS; it rejects creation, deletion, write, truncate, sync, writable memory mapping, and mutation-capable file controls. It exposes version-1 `sqlite3_io_methods` **without any `xShm*` methods**, so WAL cannot be accessed via inherited shared-memory mapping; it fails closed rather than using exclusive-locking or immutable mode to bypass this restriction. SQLite temporary operations are in memory. A hot rollback journal is reported as recovery required, never concealed, repaired or deleted by the reader.

Force a real read in a SQLite read transaction (`BEGIN` alone is not a lock); while the underlying shared lock is held, inspect the main database header through the same wrapped file handle and reject WAL or malformed headers. Keep the lock throughout validation and category read, fully buffer results, and publish them only after successful transaction and close. WAL detection is enforced independently by the lack of shared-memory methods, not a raceable preflight header check. Return a sanitized failure for WAL, hot journal, busy/unsupported locks, I/O, corrupt or unsupported schema, unsafe control requests, or inability to establish a consistent nonmutating snapshot. A concurrent writer may commit before or after a successful snapshot; no partial result is returned as success. Guarantee is conditional on cooperating SQLite processes, reliable native locks and the existing cross-process file-replacement limitation; broken network-filesystem locking and malicious replacement cannot be made safe by this wrapper alone.

The native C wrapper is a design decision, not implemented or proven by this step. A5 must confirm how it is compiled and packaged for all supported Python versions on Linux and Windows, that the wrapper registers against the *same SQLite library* used by the reader, and which file-control/mapping operations can safely pass. M1 must test the exact implementation and SQLite versions, including real independent-process WAL mode-change and hot-journal races, and fail closed if the boundary cannot be established; Linux tests are mandatory, Windows runtime is not claimed or required from the current environment. Do not ship a read-only operation by silently falling back to `mode=ro` alone, `immutable=1`, or Python APSW's inherited WAL-capable `xShm` interface. See SQLite's [locking](https://sqlite.org/lockingv3.html), [WAL](https://sqlite.org/wal.html) and [I/O methods](https://sqlite.org/c3ref/io_methods.html) references and [APSW VFS documentation](https://rogerbinns.github.io/apsw/vfs.html).

The same read-only recognition path checks a rebuild destination before source inspection. Neither clear nor rebuild automatically migrates: a recognized older store needing migration fails visibly without changing it. An empty scan, or a scan with only valid zero-category JSON, therefore does not open a writable backend or start a write transaction and makes no persistent change. For nonempty contributions, revalidate the same resolved target under the write transaction before committing; an access/version/identity failure is an error, not a different-store fallback. A5 must reconcile this mutating-command migration policy with existing registered migration behavior and Product Owner disposition if product-visible.

There are no speculative production migrations in the inspected code, but the existing storage interface supports registered migration callbacks. The proposed management restriction is therefore a forward-compatibility behavior choice, not a demonstrated current regression or an already approved decision. A5 must decide whether clear and nonempty rebuild use the registered atomic migration path or fail migration-required; either outcome must keep empty/no-category rebuild nonmutating. Do not represent the proposal as an approved policy.

| Read-only situation | Selected fail-closed behavior |
| --- | --- |
| Supported rollback-journal store, no recovery needed | Return one locked, consistent snapshot without creating, changing or removing repository files. |
| Hot rollback journal | Do not recover, remove or change it during list/preflight; report recovery required. |
| WAL mode, with or without WAL/SHM sidecars | Do not access through a path capable of changing shared memory; if a proven no-mutation snapshot is unavailable, report unsupported read-only state without creating, changing or removing sidecars. |
| Active writer or mode change racing inspection/open | Return a verified consistent snapshot only if the no-mutation boundary is enforced across the entire race; otherwise fail visibly. A pre-open filename/header check alone is insufficient. |
| Close or cleanup | Release owned handles without repository mutation; report close failure. Never repair a journal or checkpoint a WAL. |

Recovery is an explicitly separate operator-controlled action: stop competing processes and use a separately authorized SQLite-compatible recovery/migration procedure or restore a verified backup; the list or rebuild preflight does not perform recovery or automatically delete sidecars. No particular recovery command is prescribed or claimed safe for every repository.

## 6. Extraction and category mutations

Both ordinary accumulation and rebuild use the same result-bearing extraction: read each selected persisted JSON as one byte snapshot and call the injected existing envelope reader. Built-in `1.0.0` exact identity is valid/no-category; built-in `2.0.0` exact identity and custom schema ID with `custom-sha256:` plus 64 lowercase hexadecimal digits inspect `metadata.tag_candidates`. Missing/empty candidates are a successful no-category result; each candidate must be a nonempty array of valid existing tag segments. Join segments with `/`, retain complete paths and case, deduplicate exact paths and sort. If any candidate, envelope, identity or read is invalid, reject that whole input; do not require unrelated payload fields, validate against the currently configured custom schema, infer hierarchy from XMP, or call a provider. Preserve the stage's existing envelope acceptance rather than introducing stronger JSON skip criteria.

`clear` validates the selected store and performs one short `BEGIN IMMEDIATE` transaction deleting only `known_categories`; obtain the deleted count from that transaction, check stop before commit, and commit or roll back. Preserve all other tables/domains and all images/sidecars. A zero-row clear is successful. Existing triggers on protected tables are rejected by current schema validation; do not disable them or alter schema to clear. A failed begin/delete/commit reports failure without claiming removal.

`rebuild` processes each discovered sidecar independently. For each valid nonempty extracted set, open the same selected persistent store, validate and `BEGIN IMMEDIATE`; insert distinct paths with `INSERT OR IGNORE`, count actual inserts inside that transaction, check stop, commit and close. Every successful sidecar commits independently; a later bad file does not roll back prior work. Input read/extraction errors are diagnosed and scanning continues. A storage open/write/commit failure stops further updates, reports failure with confirmed and unknown outcomes distinguished below, and never redirects to memory. Under competing writers, inserted counts come from successful inserts in this command's transactions, not before/after snapshots; a concurrent clear can remove them later. Empty/no-category inputs cause no mutation. Existing 250 ms lock-contention policy remains; it bounds lock wait, not arbitrary filesystem latency.

## 7. Results, errors and concurrent operations

For rebuild, `discovered` counts unique eligible sidecars after completed discovery; `inspected` counts sidecars whose read was attempted. Each inspected input has one terminal classification: `success` (category-bearing union confirmed committed), `skip` (valid, no eligible categories), `input_failure` (read/envelope/extraction failure), `storage_failure` (a write was not committed and rollback is known), `commit_unknown` (commit outcome cannot be established), or `interrupted` (stopped before write admission or with a confirmed rollback). Count not-attempted discovered inputs separately. Thus `inspected = success + skip + input_failure + storage_failure + commit_unknown + interrupted`; `discovered = inspected + not_attempted` after complete discovery. A successful commit followed by close failure remains a success with a separate command-level close diagnostic and nonzero exit; an unknown commit is never called a rollback or retried. A signal with an unknown commit retains `commit_unknown` for the input and takes exit precedence.

Count `category_bearing` immediately when extraction succeeds with one or more paths, regardless of later storage failure or interruption; `eligible_paths` is the sum of each successfully extracted input's unique paths at that same boundary. `transactions_attempted` counts unions begun, `confirmed_committed` counts successful commit returns, and `confirmed_inserted` sums inserts in those confirmed commits only; with any unknown commit, mark the overall inserted total as incomplete, not an exact total. Thus `confirmed_committed = success` and is at most `transactions_attempted`, which is at most `category_bearing`. Example: the first of two category-bearing inputs commits two inserts and the second extracts three paths but hits an unknown commit: inspected=2, category-bearing=2, eligible-paths=5, transactions-attempted=2, success=1, commit-unknown=1, confirmed-inserted=2 (incomplete). No claim about post-command presence is made after concurrent clear.

Command exit design is `0` for complete success including no inputs/no categories, `1` for an input, selected-store, storage, validation or partial-result failure, `2` for syntax/configuration or fatal pre-execution discovery errors, and `128 + first handled signal` for interruption. Sanitized stderr identifies operation and outcome without credentials, raw SQLite messages or category values; A4 fixes exact display format. Partial committed counts accompany nonzero completion. Diagnostic paths must follow existing privacy policy, and no category content is echoed except list's requested output.

| Situation | Required behavior |
| --- | --- |
| Missing, inaccessible, corrupt or unsupported selected store | `list`, `clear`, and `rebuild` fail visibly; no fallback, initialization, alternate repository or persistent mutation. |
| Older recognized store needing migration | All three report migration required; listing never migrates, empty rebuild remains byte/directory unchanged. |
| Empty discovery or all valid no-category inputs | Exit 0, no database write/migration, zero inserted; category and unrelated state unchanged. |
| 997 category-bearing sidecars and 3 invalid inputs | Attempt all 1,000; retain additions from successful transactions, report 997 successes and 3 failures, return 1. Actual inserted paths are separately counted. |
| Failed clear or rebuild write before commit | Roll back when possible, report error and confirmed partial outcome. If rollback cannot be established, classify the transaction outcome unknown. |
| Commit returns error or process loses the commit outcome | Report outcome unknown unless rollback/noncommit can actually be established; do not retry or count its inserts as confirmed. A successful commit followed by close failure remains committed, with a separate error. |
| Signal before or during a transaction | Stop new input/transactions, roll back if stop wins before commit; if racing commit, record actual result, preserve prior commits, report `128 + signal`. Never retry an uncertain commit. |
| List concurrent with add, clear or rebuild | One SQLite read snapshot per successful list; write/recovery restrictions still apply. It may see before or after an atomic transaction, not a fabricated merge; if a safe read is unavailable, fail visibly. |
| Clear concurrent with add/rebuild/ordinary accumulation | SQLite transactions serialize; a clear committed after an add removes it, an add committed after clear can repopulate it. No scan-wide lock, no replacement rebuild and no guaranteed winner. Successful disjoint unions persist unless a later clear removes them. |

## 8. Required future verification

These are design obligations, not tests run in A3:

1. Per-image configuration precedence, null, CWD vs distinct image roots, initialized/uninitialized/inaccessible ancestry, selected failures, shared no-store memory and isolated failed-store fallbacks. Concurrent wrappers must not close or replace one another; instrument snapshots, failover, commit and close.
2. Exactly-once post-stage barriers with real selected JSON success/valid skip, later XMP failure, selected subsets, disabled accumulation, valid JSON on an excluded image, corruption, and two image-first runs; no extra provider request. Hold a provider while an independent process reads and writes state.
3. List and startup failure tests comparing database/journal/directory content before and after: valid store, missing, corrupt, permission-denied, unsupported/old migration-required, hot journal, WAL and busy/live-writer cases. Instrument the VFS to fail every attempted mutation, force races between validation/open and writer activity, and verify either a valid locked snapshot or a visible nonmutating failure. Exercise Linux at minimum; Windows packaging/runtime remains unverified until actually run there.
4. Clear injected begin/delete/commit failures, stop barriers and separate-process verification of unchanged unrelated state and sidecars. Rebuild mixed valid v1/v2/custom/no-category/invalid inputs, duplicate paths, 997+3 partial case, empty and migration-required stores, explicit/orphan sidecars, symlinks and independent depth. Verify true per-transaction insert counts and zero model/XMP calls.
5. Independent OS processes overlap list/add/clear/rebuild and ordinary processing using deterministic lock/commit barriers; assert transaction-order outcomes, short transactions, no lost successful disjoint unions absent a later clear, no assumed winner or all-or-nothing scan. Real signal barriers before/at commit verify actual persisted state and interrupted/not-attempted accounting. Inject failures immediately before, during and after commit and on close; distinguish known rollback, unknown commit and confirmed commit with close failure, with correct extraction and confirmed-insert counts. Replace a target between recognition and transaction and probe handle-bound identity guarantees rather than treating a pathname as stable identity.

## 9. Verification and acceptance

No feature implementation, provider call, live image, Windows runtime or new design-behavior test was performed. At version `0.3.9`, from the project root, `uv lock --locked` passed (21 packages), `uv run --locked --extra dev --python 3.13 image-clarus --version` reported `image-clarus 0.3.9`, and `uv run --locked --extra dev --python 3.13 pytest -q tests/unit/test_cli.py tests/unit/test_resources.py tests/unit/test_state_resolution.py tests/unit/test_state_storage.py tests/unit/test_state_categories.py tests/unit/test_state_accumulation.py` passed 118 tests. `uv run --locked --extra dev --python 3.13 ruff check .` and `uv run --locked --extra dev --python 3.13 ruff format --check .` passed (163 files). The editable-install hardlink-to-copy fallback succeeded. These are existing baseline checks, not evidence that the proposed design runs.

An isolated `uv pip install --target "$TMPDIR/image-clarus-a3-apsw" apsw` installed APSW `3.54.1.0` only under scratch, not the project environment or manifest. A scratch-import introspection probe reported SQLite `3.54.1`, `xOpen`/`xDelete`/`xAccess` hooks and file read/write/truncate/sync/lock hooks available, but `VFSFile.xShmMap` absent. This was an API-shape probe, not proof of a safe VFS or of WAL, concurrency or Windows behavior. The documented APSW behavior of inheriting native shared-memory methods is why the selected design exposes a native version-1 I/O-methods table instead. Independent source research supports the protocol concept but did not implement or validate it.

Created this A3 record; updated `docs/slice-4/IMPL-PLAN-slice-4.md`, `pyproject.toml`, `uv.lock`, `tests/unit/test_cli.py`, and `tests/unit/test_resources.py` to synchronize progress and the patch version. No other implementation or behavior test was changed. Independent review exposed the read-only VFS race, uncertain commit accounting, target-identity races and product-visible management choices; the record incorporates these findings, and remaining acceptance stays open.
