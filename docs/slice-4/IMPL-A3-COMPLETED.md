# Step A3 - Freeze state and category management contracts [DESIGN]

**Status:** Design complete historically; the subsequent Product Owner SQLite decision below supersedes the former native reader selection. The capability-aware target identity contract remains. No Slice 4 management command, batch state engine, or acceptance test is implemented here. Linux feasibility evidence is limited and Windows runtime behavior is unverified.

**Subsequent reconciliation:** [A5](IMPL-A5-COMPLETED.md) made the non-migrating-open and atomic first-mutation sequence explicit. The current logical read-only and empty-safe contracts are in §5; earlier versioned test evidence is unchanged.

**Subsequent scratch feasibility:** A5 records Linux-only synthetic VFS tests showing rollback-mode reads, lock contention, and fail-closed hot-journal/WAL behavior under the tested conditions. The previously selected native design is superseded as described in §5. The probe is not production or cross-platform proof.

**Further A5 investigation (historical):** Separate Linux scratch probes support limited rollback-lock interoperability and show that ordinary reads can update filesystem access times. The prior WAL no-write boundary is superseded by the current decision in §5; neither probe establishes a portable reader.

**Scope deviations:** None. The Product Owner approved CWD-selected management state, registered migrations for clear and nonempty rebuild, and explicit/orphan sidecar inputs; list and empty/no-category rebuild never migrate.

## 1. Scope and dependency boundaries

Current state selection, optional fallback, storage and extraction are implemented in `src/image_clarus/state/resolution.py`, `service.py`, `storage.py` and `accumulation.py`; the existing CLI calls optional accumulation after `run_pipeline`. The existing `StateService` mutates its own backend on failure, `MemoryStorage` is not synchronized, and the writable SQLite constructor can migrate. None is a suitable shared mutable management facade or a provably read-only list backend. `_extract` accepts an injected envelope reader; the reader currently lives in `stages/structure.py`. Preserve that direction through composition: management and batch wiring inject the existing authoritative envelope reader into a result-bearing extractor in `state/accumulation.py`; the state domain does not import stages or duplicate the envelope validator. A5 checks that ownership and public compatibility remain correct.

Selected additions are `src/image_clarus/state/management.py` for strict command orchestration and result types and `src/image_clarus/state/readonly.py` for read-only SQLite access using Python's standard library. The earlier `readonly_vfs.c` selection is superseded. Retain the single authoritative extraction implementation in `state/accumulation.py` with its injected reader; do not introduce a duplicate extraction module. Extend `state/storage.py` with strict category-only delete and transactional insert counts; A1's `discovery.py` provides enumeration. CLI composes these pieces without importing a provider or XMP backend for management. Selected tests include `tests/unit/test_state_management.py`, `tests/unit/test_state_readonly.py`, `tests/integration/test_state_management_cli.py`, and `tests/integration/test_state_management_concurrency.py`, plus existing state and pipeline tests. These paths are design selections, not claims that files exist.

## 2. Ordinary process: per-image selection and ownership

Configuration priority is dedicated `--state-dir` > ordered `--set` > selected YAML > defaults. A dedicated/`--set` relative path is relative to CWD; YAML-relative values resolve relative to the YAML file, preserving existing origin handling. An effective null clears a lower selection and resumes discovery. Resolve once per image's context, not once per batch; hold that image's context for all prompt snapshots and its finalization.

| Condition | Selection and ordinary-processing outcome |
| --- | --- |
| Explicit/effective non-null directory | Select exactly that directory for every image; no ancestor search. A valid repository can be shared through independent handles. |
| Explicit selected directory missing, invalid, inaccessible, corrupt or unsupported | Emit sanitized state diagnostic and use that image's temporary memory; never select another persistent repository. |
| No explicit directory; nearest initialized CWD ancestor | Select it for each image even when an image is under a different initialized collection. A selected but invalid candidate is an error, not permission to search elsewhere. |
| No CWD candidate; nearest initialized image-directory ancestor | Select independently for each image. Different collection roots can select different repositories. |
| Accessible ancestor `.image-clarus` directory without database | It is uninitialized; continue searching. An inaccessible/broken entry is an error, not absence. |
| Neither ancestry has an initialized repository | Use shared invocation-local no-store memory, with no diagnostic and no persistent creation. |
| Discovery, open, read, update, migration or close error | Report a sanitized, image-correlatable state diagnostic independent of logging level; preserve otherwise-valid stage results, do not redirect to another persistent store, and use only the affected image's isolated temporary fallback as applicable. |

The coordinator owns a separate service wrapper and lifecycle token for each image; persistent backends use independent handles to the same resolved identity and short transactions. A shared synchronized memory backing serves all images that genuinely selected no repository, allowing image-first runs to see previous no-store additions; each wrapper releases its reference after finalization and the coordinator closes that backing after all images drain. A failing selected-store wrapper switches only itself to fresh per-image memory; it never swaps another image's backend or closes its live handle. A failed read yields an empty snapshot. A failed union rolls back, diagnoses and is not replayed into memory; only later successful additions to that fallback can be observed by that image. Existing SQLite bounded contention and sanitized diagnostics apply; no transaction, cursor or lock spans a provider request, a stage operation, or the full batch. This invocation-wide no-store memory behavior is a batch design decision, not an assertion about prior multi-image behavior.

## 3. Actual-result finalization

The coordinator owns exactly-once post-selected-stage finalization, including when a later selected stage fails, a stage is budget-bypassed, or a handled stop arrives. Finalization is not synonymous with performing optional accumulation. Each eligible image's service is closed after its own finalization; duplicate terminal messages cannot repeat a union.

| Actual image outcome | Optional category accumulation |
| --- | --- |
| Selected JSON `completed`, or selected JSON `skipped/output_exists` | If enabled and no stop is observed, read the actual `.desc.json` bytes once after selected stages terminate; validate/extract and union once. The later stage can have failed; retain its failure. |
| Known budget-excluded image with valid selected JSON authoritatively confirmed `output_exists` | Same eligible path, without inference. Record budget classification separately from real JSON result. |
| Budget-excluded skip, omitted JSON, JSON failure/missing prerequisite or no actual JSON result | No accumulation, even if a file exists. A prediction or budget bypass is never `output_exists`. |
| Disabled, dry run, or handled stop observed before optional work | Do not read JSON for accumulation or open/update state for it. Dry run also does not open, initialize, migrate or write state at any stage. |
| Eligible JSON missing, unreadable, invalid, or replaced after stage | Sanitized optional error; do not regenerate, invent a result or change the primary stage result. Use the actual bytes read; lock-free external sidecar replacement remains possible. |
| State update interrupted before commit | Roll back and close; never replay. If stop races an already executing commit, report the real committed/rolled-back outcome and signal result; no sidecar-state atomicity is implied. |

Sequential mode completes this finalization and closes the image wrapper before beginning the next image. Concurrent images may snapshot at different times; no global taxonomy barrier is added. Check stop before starting an optional operation, before a transaction and immediately before commit; state errors remain visible and nonblocking while `StateStopped` is interruption, not a fallback diagnostic.

## 4. Management grammar and target

The following are chosen CLI designs, not implemented commands:

```text
image-clarus state categories list [--config FILE] [--set PATH=VALUE] [--state-dir DIR]
image-clarus state categories clear [--config FILE] [--set PATH=VALUE] [--state-dir DIR]
image-clarus state categories rebuild SOURCE... [--config FILE] [--set PATH=VALUE] [--state-dir DIR] [--max-depth N | --max-depth-unlimited]
```

Options belong to the operation and obey A1 singleton/conflict and source-origin rules. Resolve only configuration relevant to state and, for rebuild, selection; do not require credentials, provider, stage, prompt/schema or XMP preflight. The destination is one repository for the entire command: effective dedicated CLI directory, then generic override/YAML directory, else nearest initialized CWD ancestor. A null resets lower selection to CWD discovery. Without a selected initialized repository, fail visibly; no temporary-memory success, automatic initialization, image-ancestor discovery, or alternate persistent fallback. Rebuild source roots are inputs only and do not choose a destination; for a source outside the CWD collection the user supplies `--state-dir` as needed. An explicit invalid selection fails, and an accessible uninitialized ancestor is skipped during discovery as in ordinary processing. The Product Owner approved this CWD-selected destination with an explicit state-directory override.

Example: with an initialized CWD repository A and source collection B, rebuilding B without a directory option targets A, not B; to target B, pass B's repository directory explicitly. Multiple source roots likewise use only that single selected destination. Before any mutation report the target-selection origin (explicit/configured or CWD-discovered) in the operation summary; do not print credentials, category data, raw SQLite errors, or path text in diagnostics. Resolve and retain the selected repository path throughout the command and never substitute a different path. Detect replacement using reliable filesystem identity where supported; a detected replacement fails instead of silently switching repositories. Absence of optional stable identity capability alone is not a failure. These checks cannot close a cross-process replacement race after the last check, so do not claim strict pinned-target safety; report a genuinely ambiguous replacement or commit as uncertain rather than asserting an update reached the intended repository. Test supported and unavailable identity capabilities, and replacement before open, during a write and immediately before commit.

Rebuild accepts explicit `.desc.json` files, directories and A1 native patterns; discovery includes orphan sidecars whether or not the corresponding image exists, as approved by the Product Owner. Existing explicit-file symlinks follow A1's literal-file rule; discovered symlinks are not followed. Native patterns use A1's case-sensitive default and invocation-only `-i` / `--ignore-case` option without changing resolved identity. Deduplicate overlapping inputs by A1 resolved identity; process in A1 deterministic traversal order with the independent `category_rebuild.max_depth` and depth flags. Each explicit file is eligible by suffix; no sidecar is selected by inspecting its image, XMP, or decoder. Discovery/invalid-source errors prevent mutation and return a command/config error; after completed discovery, individual read/extract errors are per-input failures and do not stop other readable inputs.

## 5. Strict read-only listing and empty-safe access

**Current Product Owner decision — supersedes the native selection and physical no-write boundary below.** Use Python standard-library `sqlite3` for logical read-only access: listing must not change application data or schema, initialize a store, or run migrations. SQLite and the OS may perform their normal journal/WAL/shared-memory and access-time operations. Do not restore timestamps. Remove the native VFS, bundled SQLite, C extension, detached snapshot, and their special packaging from the active design; Windows and Linux use an ordinary Python installation. Clear and a nonempty rebuild may apply registered migrations transactionally with their mutation; an empty/no-category rebuild makes no persistent mutation. The former design and its table below are retained solely as historical evidence, not active requirements or proof of implementation. Future implementation and tests must verify the new logical contract, not the former sidecar nonmutation contract.

### Superseded design record (historical)

A list selects an existing target, opens it without initialization/migration, validates application ID, format/domain version and schema, and returns a consistent binary-sorted snapshot. It does not write, create or remove the directory, DB, journal, WAL or shared-memory file, even on error. The Product Owner permits normal filesystem-maintained access-time updates resulting from reads; do not restore timestamps by writing them back. Corruption, access failure, unsupported/newer version or recognized older version needing migration is a sanitized error, not an empty list. No management command selects memory. Ordinary `SQLiteStorage`, `_connect(mode=rw)` and `immutable=1` on a concurrently writable live DB do not meet this contract.

**Selected design: native fail-closed SQLite VFS and detached snapshot.** Implement `src/image_clarus/state/readonly_vfs.c` as a CPython extension and `src/image_clarus/state/readonly.py` as its adapter. The extension contains one pinned, vendored official SQLite amalgamation (3.53.1, including its license) and registers its wrapper with that same embedded SQLite instance; it never relies on loading an extension into Python's independently linked SQLite. Build the extension and amalgamation together via a setuptools build backend, publishing platform wheels for supported Linux and Windows/Python combinations and a source distribution requiring a working C toolchain. Hide bundled SQLite symbols outside the extension to prevent process-level interposition; Windows exports only the Python extension entry point. No system SQLite headers, extension-loading capability, APSW, or separate executable is required. The build and wheel paths are M1 implementation obligations, not evidence of an existing package or Windows build.

The native wrapper delegates to that embedded SQLite's platform default VFS for truthful path/access checks, reads and native SQLite locking. Open only the existing main database and needed existing rollback journal with `SQLITE_OPEN_READONLY` and private cache; reject every create, delete, write, truncate and sync operation. Use version-1 file methods with no `xShm*` or mapped `xFetch`, and configure temporary storage in memory. Forward only reviewed read-only file-control operations necessary for the delegated platform VFS and return `SQLITE_NOTFOUND` or a safe error for all others; never forward controls that can mutate or bypass the boundary. Disable extension loading. The wrapper denies mutations rather than trusting a header precheck, so a concurrent journal-mode transition cannot open a writable escape path.

After opening, start a read transaction and execute an actual read to acquire SQLite's lock (`BEGIN` alone is insufficient). While the transaction and lock are held, use the embedded SQLite's serialization API to take a coherent complete database snapshot; reject errors and allocation failures, and release the lock/handles without changing source files. Deserialize the detached bytes into an in-memory Python SQLite connection; reuse the authoritative storage schema/version validation and binary ordering there, returning results only after validation and cleanup succeed. Recognition for rebuild uses the same snapshot and distinguishes a recognized older store from corruption; list reports migration required. No partial results are success. The copy has database-sized memory cost, reported as an implementation constraint, not an arbitrary new product limit. Normal OS access-time changes are allowed; never restore timestamps. A selected-path identity check where reliable detects replacement without requiring optional identity support; a detected or genuinely ambiguous replacement fails visibly, and no race-free pathname pinning is claimed.

This choice uses SQLite itself for its rollback lock protocol and hot-journal classification instead of reimplementing Linux and Windows byte-range locks. The existing Linux VFS probe supports this direction but is not production or Windows proof. Plain `mode=ro`, live `immutable=1`, independently copied live files, inherited APSW shared-memory methods and the unproven raw-lock snapshot are not substitutes; an OS sandbox would introduce a separate platform policy/deployment boundary. A cold rollback journal alone is not a failure; recovery-required journals and unsafe WAL fail clearly without mutation. No unsafe fallback is allowed if the extension is unavailable. M1 must build and test the chosen implementation, including real independent-process mode-change and hot-journal races; Linux tests are mandatory, Windows runtime is not claimed or required from the current design environment. See SQLite's [locking](https://sqlite.org/lockingv3.html), [WAL](https://sqlite.org/wal.html) and [I/O methods](https://sqlite.org/c3ref/io_methods.html) references.

### Current migration contract

The Product Owner approved registered migrations for `clear` and a rebuild with eligible categories. Listing never migrates. Rebuild first recognizes its target without logical data/schema mutation and scans inputs; a recognized older store is not itself a reason to migrate during this phase. With no eligible categories, including an empty scan, it makes no persistent change and never opens a writable backend. On the first nonempty contribution, revalidate the same selected target, apply any registered migration atomically with that first union, and commit or roll back together; subsequent unions use short transactions. Clear similarly applies any registered migration and the category-only clear in one transaction. Missing/unregistered or failed migration is visible, rolls back when known, never selects another store, and uses the unknown-commit reporting contract where applicable. A migration may change only its registered application-owned schema/domain data; clear itself deletes only categories. There are no speculative production migrations in the inspected code. Define a recognition result that distinguishes a supported older store requiring registered migration from a corrupt or unsupported store; `list` reports migration required rather than returning that internal result as successful output.

### Superseded physical-boundary scenarios (historical)

| Read-only situation | Required fail-closed behavior of the selected design |
| --- | --- |
| Supported rollback-journal store, no recovery needed | Return one locked, consistent snapshot without application creation, writes or removal of repository files; normal OS-maintained access-time changes are permitted. |
| Hot rollback journal | Do not recover, remove or change it during list/preflight; report recovery required. |
| WAL mode, with or without WAL/SHM sidecars | Do not access through a path capable of changing shared memory; if a proven no-mutation snapshot is unavailable, report a clear error without creating, writing or removing sidecars. Safely reading a WAL snapshot remains permitted. |
| Active writer or mode change racing inspection/open | Return a verified consistent snapshot only if the no-mutation boundary is enforced across the entire race; otherwise fail visibly. A pre-open filename/header check alone is insufficient. |
| Close or cleanup | Release owned handles without repository mutation; report close failure. Never repair a journal or checkpoint a WAL. |

Recovery is an explicitly separate operator-controlled action: stop competing processes and use a separately authorized SQLite-compatible recovery/migration procedure or restore a verified backup; the list or rebuild preflight does not perform recovery or automatically delete sidecars. No particular recovery command is prescribed or claimed safe for every repository.

## 6. Extraction and category mutations

Both ordinary accumulation and rebuild use the same result-bearing extraction: read each selected persisted JSON as one byte snapshot and call the injected existing envelope reader. Built-in `1.0.0` exact identity is valid/no-category; built-in `2.0.0` exact identity and custom schema ID with `custom-sha256:` plus 64 lowercase hexadecimal digits inspect `metadata.tag_candidates`. Missing/empty candidates are a successful no-category result; each candidate must be a nonempty array of valid existing tag segments. Join segments with `/`, retain complete paths and case, deduplicate exact paths and sort. If any candidate, envelope, identity or read is invalid, reject that whole input; do not require unrelated payload fields, validate against the currently configured custom schema, infer hierarchy from XMP, or call a provider. Preserve the stage's existing envelope acceptance rather than introducing stronger JSON skip criteria.

`clear` validates the selected store and performs one short `BEGIN IMMEDIATE` transaction deleting only `known_categories`; obtain the deleted count from that transaction, check stop before commit, and commit or roll back. Preserve all other tables/domains and all images/sidecars. A zero-row clear is successful. Existing triggers on protected tables are rejected by current schema validation; do not disable them or alter schema to clear. A failed begin/delete/commit reports failure without claiming removal.

`rebuild` processes each discovered sidecar independently. For each valid nonempty extracted set, open the same selected persistent store, validate and `BEGIN IMMEDIATE`; insert distinct paths with `INSERT OR IGNORE`, count actual inserts inside that transaction, check stop, commit and close. Every successful sidecar commits independently; a later bad file does not roll back prior work. Input read/extraction errors are diagnosed and scanning continues. A storage open/write/commit failure stops further updates, reports failure with confirmed and unknown outcomes distinguished below, and never redirects to memory. Under competing writers, inserted counts come from successful inserts in this command's transactions, not before/after snapshots; a concurrent clear can remove them later. Empty/no-category inputs cause no mutation. Existing 250 ms lock-contention policy remains; it bounds lock wait, not arbitrary filesystem latency.

For an older recognized store, this sequence means specifically: nonmutating recognition before discovery; scan until the first valid nonempty category contribution; only then open the same selected path without a migration-capable constructor, check optional reliable replacement identity, acquire `BEGIN IMMEDIATE`, revalidate the version while holding the transaction, apply the registered migration and first union within that same transaction, check stop, then commit or roll back together. The clear path performs the same transactional migration-and-delete sequence. A constructor that silently commits migration before the union/delete is prohibited. A missing registration, migration error or known rollback fails visibly; an uncertain commit is reported as such. No-category scans never enter this sequence. These are future implementation/test obligations, not an assertion the existing constructor already supports them.

## 7. Results, errors and concurrent operations

For rebuild, `discovered` counts unique eligible sidecars after completed discovery; `inspected` counts sidecars whose read was attempted. Each inspected input has one terminal classification: `success` (category-bearing union confirmed committed), `skip` (valid, no eligible categories), `input_failure` (read/envelope/extraction failure), `storage_failure` (a write was not committed and rollback is known), `commit_unknown` (commit outcome cannot be established), or `interrupted` (stopped before write admission or with a confirmed rollback). Count not-attempted discovered inputs separately. Thus `inspected = success + skip + input_failure + storage_failure + commit_unknown + interrupted`; `discovered = inspected + not_attempted` after complete discovery. A successful commit followed by close failure remains a success with a separate command-level close diagnostic and nonzero exit; an unknown commit is never called a rollback or retried. A signal with an unknown commit retains `commit_unknown` for the input and takes exit precedence.

Count `category_bearing` immediately when extraction succeeds with one or more paths, regardless of later storage failure or interruption; `eligible_paths` is the sum of each successfully extracted input's unique paths at that same boundary. `transactions_attempted` counts unions begun, `confirmed_committed` counts successful commit returns, and `confirmed_inserted` sums inserts in those confirmed commits only; with any unknown commit, mark the overall inserted total as incomplete, not an exact total. Thus `confirmed_committed = success` and is at most `transactions_attempted`, which is at most `category_bearing`. Example: the first of two category-bearing inputs commits two inserts and the second extracts three paths but hits an unknown commit: inspected=2, category-bearing=2, eligible-paths=5, transactions-attempted=2, success=1, commit-unknown=1, confirmed-inserted=2 (incomplete). No claim about post-command presence is made after concurrent clear.

Command exit design is `0` for complete success including no inputs/no categories, `1` for an input, selected-store, storage, validation or partial-result failure, `2` for syntax/configuration or fatal pre-execution discovery errors, and `128 + first handled signal` for interruption. Sanitized stderr identifies operation and outcome without credentials, raw SQLite messages or category values; A4 fixes exact display format. Partial committed counts accompany nonzero completion. Diagnostic paths must follow existing privacy policy, and no category content is echoed except list's requested output.

| Situation | Required behavior |
| --- | --- |
| Missing, inaccessible, corrupt or unsupported selected store | `list`, `clear`, and `rebuild` fail visibly; no fallback, initialization, alternate repository or persistent mutation. |
| Older recognized store needing a registered migration | List reports migration required without changes; clear and first eligible rebuild contribution may migrate transactionally; empty/no-category rebuild never migrates. An unsupported or failed migration reports failure. |
| Empty discovery or all valid no-category inputs | Exit 0, no application data/schema mutation or migration, zero inserted; category and unrelated state unchanged. Normal SQLite and OS read-related operations remain permitted. |
| 997 category-bearing sidecars and 3 invalid inputs | Attempt all 1,000; retain additions from successful transactions, report 997 successes and 3 failures, return 1. Actual inserted paths are separately counted. |
| Failed clear or rebuild write before commit | Roll back when possible, report error and confirmed partial outcome. If rollback cannot be established, classify the transaction outcome unknown. |
| Commit returns error or process loses the commit outcome | Report outcome unknown unless rollback/noncommit can actually be established; do not retry or count its inserts as confirmed. A successful commit followed by close failure remains committed, with a separate error. |
| Signal before or during a transaction | Stop new input/transactions, roll back if stop wins before commit; if racing commit, record actual result, preserve prior commits, report `128 + signal`. Never retry an uncertain commit. |
| List concurrent with add, clear or rebuild | One SQLite read snapshot per successful list; the logical read-only contract applies. It may see before or after an atomic transaction, not a fabricated merge; if a consistent read is unavailable, fail visibly. |
| Clear concurrent with add/rebuild/ordinary accumulation | SQLite transactions serialize; a clear committed after an add removes it, an add committed after clear can repopulate it. No scan-wide lock, no replacement rebuild and no guaranteed winner. Successful disjoint unions persist unless a later clear removes them. |
