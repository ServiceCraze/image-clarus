### Superseded portable read-only design and historical evidence

The following former physical no-write design and feasibility evidence are retained for provenance only; the current Product Owner decision above governs instead. In particular, neither the native reader nor its special packaging is an active implementation obligation.

The existing `state/storage.py` constructor opens writable and may migrate. Strict `list` forbids application writes, creation or removal of database, journal, WAL, shared memory or directory even when opening fails; ordinary OS-maintained access-time updates from reading are permitted. SQLite `mode=ro` alone does not prove WAL sidecars cannot be modified; `immutable=1` against a live writable database disables needed locking/change detection; copying live DB/WAL files independently is not a coherent snapshot. The chosen wrapper must be tested for denied mutation paths and SQLite locks, and its Linux/Windows packaging and same-library registration must be implemented as specified in A3. A pre-open header/sidecar test alone races a writer. Fail visibly rather than fall back to an unsafe reader, report unavailable safe reads including hot-journal/WAL cases truthfully, and do not impose optional filesystem-identity support as a blanket prerequisite.

The native VFS is selected as the design in A3 §5; no unverified Python APSW shared-memory interception is claimed. References: [SQLite WAL](https://sqlite.org/wal.html), [SQLite locking](https://sqlite.org/lockingv3.html), [SQLite URI](https://sqlite.org/uri.html), [SQLite backup](https://sqlite.org/backup.html), [SQLite VFS](https://sqlite.org/c3ref/vfs.html). M1/M3 must ultimately exercise real independent-process read/write, WAL, hot-journal, mode-change, open/close/failure races and nonmutation. The native extension, its packaging and Windows behavior are not yet implemented or verified.

An additional standard-library candidate is an isolated helper that acquires SQLite-compatible OS byte-range read locks, reads a rollback-mode database as bytes under that lock, then validates an in-memory deserialized snapshot without opening the source through SQLite. This is **not selected**: matching the deployed SQLite VFS locking protocol on Linux and Windows, correctly distinguishing cold from hot journals under races, identity/replacement and memory costs remain unresolved. A file copy without compatible locks is not a safe substitute. A3 requires successful supported rollback-mode reads when recovery is unnecessary, not blanket rejection of every existing journal. No Windows lock interoperability test was performed.

**Additional rollback-lock and filesystem evidence:** An isolated Linux scratch probe observed a SQLite reader return the pre-transaction value while an independent writer held a RESERVED lock with a journal present. In a separate-process probe, holding a shared-byte-range lock made the writer's commit report `database is locked`; commit succeeded after release. This supports only those tested cases. POSIX record locks are process-associated, so the initial same-process attempt was not valid cross-process evidence. A separate ordinary synthetic file read changed an intentionally old access time; an `O_NOATIME` read did not on that Linux filesystem. The latter flag is permission- and filesystem-dependent and is not a portable guarantee. Do not restore timestamps after a read: that is itself a mutation and can race. These observations are not tests of the application, Windows, full journal classification or all filesystem behavior.

The Product Owner resolved the previously ambiguous boundary: ordinary OS-maintained access-time updates from reads are permitted, and a WAL repository must yield a clear error if it cannot be read safely without application writes; safe WAL reads remain permitted. Neither a new arbitrary snapshot-size limit nor mandatory Windows runtime testing is an approved prerequisite. Windows remains an expected platform by design, while no Windows test machine is required for the current design step.

### Subsequent isolated feasibility probes (historical)

These probes used synthetic data on Linux only, not product code or live providers. They inform the tradeoffs but do not establish a portable SQLite mechanism or demonstrate Slice 4 behavior.

- **Native SQLite VFS:** A scratch C wrapper using Python 3.14.9 and SQLite 3.53.1 rejected mutating VFS methods, omitted shared-memory methods, and forwarded native locking. A rollback-mode database was read with no observed inventory changes; a synthetic hot journal returned `SQLITE_READONLY_ROLLBACK`, and live WAL returned `SQLITE_CANTOPEN`, again with no observed inventory changes. Independent reader/writer contention produced `SQLITE_BUSY` until the opposing lock released. In one race, 500 writer commits coincided with 216 successful reader queries and 284 busy results; a reader-only trace found no identified target-mutating syscalls within its selected syscall/path filters. Non-race inventories compared names, sizes, mtime, ctime and content hashes, not access times. This is promising evidence for fail-closed rollback-mode access, **not** proof for all mutation paths, hostile paths, races, VFS variants, filesystems or Windows. It does not support live WAL listing. An initial prototype crashed because its registered extension was unloaded; keeping it permanently loaded fixed subsequent runs. Native build/distribution, extension-loading availability and registration with the reader's SQLite library remain unresolved; see [SQLite loadable extensions](https://www.sqlite.org/loadext.html) and [Python sqlite3 extension loading](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.enable_load_extension).
- **Async transport:** A loopback server held responses while an `httpx.AsyncClient` task was cancelled. Across three runs before headers and three after partial body delivery, cancellation completed, the client closed, and the server observed EOF without releasing the response. This was Python 3.14.9, httpx 0.28.1, httpcore 1.0.9, `timeout=None`, `trust_env=False`, and the Linux asyncio selector loop. It demonstrates cooperative cancellation at these network-await points only: it does not establish interruption of synchronous request construction or response parsing, Windows behavior, remote computation/billing cancellation, application shutdown deadlines, or comparative subprocess performance. A5 selected the subprocess with the tradeoffs and compatibility obligations in A2, not because the probe proved async unusable.
